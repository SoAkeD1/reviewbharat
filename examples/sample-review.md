### [CRITICAL] SQL Injection Vulnerability
`app/db.py:13`

The `get_user` function constructs the SQL query using string concatenation with the `name` parameter. This allows an attacker to inject arbitrary SQL commands (e.g., `name = "'; DROP TABLE users; --"`), leading to data loss or unauthorized access.

**Suggestion:** Use parameterized queries to safely bind the `name` parameter. Example: `cur = conn.execute("SELECT * FROM users WHERE name = ?", (name,))`

### [CRITICAL] Use of eval() for User Input
`web/calc.js:4`

The `run` function uses `eval()` to execute the `expr` string. If `expr` comes from user input, this allows arbitrary code execution, leading to remote code execution (RCE) vulnerabilities.

**Suggestion:** Avoid `eval()`. Use a safe expression parser or a dedicated math library. If `eval` is absolutely necessary, sandbox it in a Web Worker or use a library like `mathjs`.

### [HIGH] Hardcoded API Key
`app/db.py:13`

The `API_KEY` is hardcoded in the source code. This exposes the secret to anyone with access to the repository and makes rotation difficult. It is a significant security risk.

**Suggestion:** Move the API key to an environment variable or a secure secrets manager. Example: `API_KEY = os.environ.get("API_KEY")`

### [MEDIUM] Bare Except Clause
`app/db.py:18`

The `except:` block catches all exceptions, including `SystemExit` and `KeyboardInterrupt`, and silently swallows them. This makes debugging difficult and can hide critical errors.

**Suggestion:** Catch specific exceptions (e.g., `sqlite3.Error`) and log the error or re-raise it. Example: `except sqlite3.Error as e: logger.error(e)`
